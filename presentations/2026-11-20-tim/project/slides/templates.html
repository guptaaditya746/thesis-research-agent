1 · The protocol

One template per answer kind: the plan only fills its blanks

Effect

“Does A improve M compared with B?”

Person checks: threshold for “no effect”, which measure counts, same setting only

Answer: per paper better / worse / no difference → supported, refuted, mixed, no effect, insufficient

Consistency

“Do the authors’ claims match their numbers?”

Person checks: threshold below which a difference is “no effect”

Answer: per claim, agrees or disagrees with the paper’s own numbers

Inventory

“Which X were studied?”

Person checks: the target: things compared, or measures

Answer: every distinct name, with the papers that name it

Best

“Which is best on M?”

Person checks: count wins per result or per paper; which direction is better

Answer: the thing with the most wins, with the counts

Open (written)

“It depends”, “cannot tell”, mixed questions

Person checks: the same decisions, line by line

Answer: a model writes 1–8 sentences; code checks every number against the cited facts

Claims check (always added)

“Do the conclusions match the numbers?”

Added to: every effect and consistency plan, by code; cannot be removed

Answer: firm “improves” claims no comparison backs, shown as a caveat

Templates: backend/evidence/kg/templates/*.rq (effect, consistency, inventory, best, oversell)

Each kind has a fixed recipe, a SPARQL template. The plan only fills in the blanks, and the person checks what goes into them. That is what makes the answer predictable: for an effect question, the label follows mechanically from the per-paper comparisons. Open questions are the exception: a model writes the text, but code still checks every number. The claims check is always added; it catches authors who claim more than their numbers show, which synth3 plants on purpose.
